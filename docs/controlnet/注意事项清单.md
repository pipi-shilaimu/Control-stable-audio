# StableAudio ControlNet 替换 `ContinuousTransformer` 注意事项清单

> 记录日期：2026-04-14  
> 适用范围：当前仓库 `stable_audio_control/models/control_transformer.py` 与 `stable_audio_control/models/control_dit.py` 的接入方案（就地替换 transformer + 旁路 control 输入）

## 1) 当前方案是否稳当（结论）

- 当前替换路径在工程上是可行的，核心调用链已打通：`ConditionedDiffusionModelWrapper -> DiTWrapper -> DiffusionTransformer -> transformer`。
- `control_input=None` 时会退回原始主干路径，能保证不传控制条件时行为一致。
- `zero_linear` 全零初始化策略合理，符合 ControlNet 训练初期“尽量不扰动基模”的原则。

## 2) 最容易踩坑的技术点

- **输入形状约束**
  - `control_input` 目标形状是 `[B, S, dim_in]`（token 视角），不是 `[B, C, T]`。
  - 若 `patch_size > 1`，`S` 不是 `T`，需要显式对齐 token 长度。
- **CFG 批次扩展**
  - DiT 在 CFG 路径会把 batch 变成 `2B`；`control_input` 必须同步扩展，否则 batch mismatch。
- **长度对齐语义**
  - 当前采用 `nearest` 插值对齐序列长度，训练前需确认这是否符合旋律控制语义（避免节拍/音高信息被粗糙拉伸）。
- **dtype/device 对齐**
  - 需与模型参数 dtype 一致；半精度下尤其要避免控制分支张量残留在 fp32 或 CPU。

## 3) 训练前必须确认的策略点

- **冻结范围**
  - `freeze_base()` 仅冻结 transformer 主干；默认训练 wrapper 会优化 `self.diffusion.parameters()` 全量参数。
  - 必须明确是否还要冻结 pretransform、原生 conditioner、DiT 其他模块，否则训练成本和不稳定风险会升高。
- **可训练参数集合**
  - 建议只训练：`control_layers`、`zero_linears`、`control_projector`（和后续 melody conditioner）。
  - 建议显式打印 trainable 参数清单做一次核对。
- **conditioning 路由**
  - 当前是旁路 `melody_control -> control_input`，不走 `*_cond_ids` 主链；这能工作，但要自行维护与训练/推理脚本的一致性。

## 4) 与训练生态集成的风险点

- **Demo 回调可能“看不到”控制效果**
  - 默认 demo 多走 `get_conditioning_inputs` 路径；若未把 `melody_control` 在 demo 流程中注入 forward，demo 结果可能失真。
- **配置一致性**
  - `sample_size`、`min_input_length`、pretransform 下采样比、patch size 必须一致，否则高概率 shape 错误。
- **数据时长与有效训练长度一致**
  - Stable Audio Open 默认 `sample_size=2097152`，44100 Hz 下约 47.55 秒。
  - 如果训练集是 10 秒切片，必须显式使用 `--seconds-total 10` 或等价 `--sample-size`，否则每条样本会被补大量 0，控制分支容易学到静音/平滑偏置。
  - 启动日志里优先看 `effective_train_sample_size`，不要只看 `model_config_sample_size`。
- **Demo 消融必须完整**
  - 只听 `control_scale=1.0` 不足以判断学会控制；它可能只是更强的坏 residual。
  - 至少保留 `control_scale=0,0.1,0.3,0.6,1.0`，并比较 `correct`、`shuffled`、`zero` 三种 `control_variant`。
  - 如果三种 variant 听起来差不多，说明模型大概率还没学到 melody-specific control。
- **Demo 成本要先控住**
  - 默认 demo 网格是 `demo_cfg_scales=[3,6,9]`、5 个 `control_scale`、3 个 `control_variant`，一轮是 45 次采样。
  - 第一次 smoke 建议用 `--demo-cfg-scales 6 --demo-steps 30 --demo-control-scales 0,1 --demo-control-variants correct,zero`，先压到 4 次采样。
  - 链路确认无误后，再扩大 control scale / variant 网格听质量。
- **Demo 旋律源要可控**
  - 默认 demo 使用当前训练 batch 的音频提取旋律，适合看训练同源样本。
  - 如果要长期观察某首指定旋律，训练时加 `--demo-control-audio <path>`。
  - `control_variant` 是诊断变体，不是源文件；`stem` 是输出 wav 的文件名主体。
- **pre-encoded 模式**
  - 若使用预编码数据，注意 pretransform scale 与 latent 长度/掩码同步。

## 5) 开训前最小验收清单（建议）

- Smoke-1：`control_scale=0` 与 `control_scale>0` 在 zero-init 下输出近似一致（差值接近 0）。
- Smoke-2：微扰任一 `zero_linear` 后输出差值应变为非零（证明控制路径有效）。
- Smoke-3：走一次 `DiffusionCondTrainingWrapper.training_step`，确认无 batch/shape/dtype 错误。
- Smoke-4：确认 optimizer 实际只覆盖预期参数集合（非目标模块无梯度或未被优化）。
- Smoke-5：确认启动日志里的 `effective_train_sample_size` 与数据切片时长一致，10 秒数据应接近 `10.03s` 而不是 `47.55s`。
- Smoke-6：第一次开 demo 时先用 `--demo-cfg-scales 6 --demo-steps 30 --demo-control-scales 0,1 --demo-control-variants correct,zero` 控制成本。
- Smoke-7：正式诊断时确认输出同时覆盖多个 `control_scale` 与 `correct/shuffled/zero`，并能用 `--demo-control-audio` 固定旋律源。

## 7) VAE encoder 非确定性（2026-05-23 新增）

### 症状
单 batch 过拟合训练 loss 长期不降（25000 步仍 0.7-0.9），即使 backbone 全参数训练也无法收敛。

### 根因
`pretransform.encode()` → `VAEBottleneck.encode()` → `vae_sample()` 每步调用 `torch.randn_like(mean)`，
生成不同的 latent。`torch.no_grad()` 和 `eval()` 都无法阻止。这是 upstream `stable_audio_tools` 的设计行为——VAE 重参数化需要每步采样。

### 修复
训练时绕开 VAE bottleneck，直接用 encoder 的 mean 输出：

```python
# 替換 pretrainform.encode(reals)
with torch.no_grad():
    raw = pretransform.model.encoder(reals)       # [B, 128, L]
    latent = raw[:, :64, :] / pretransform.scale  # 前 64 通道 = mean
```

验证：固定 t=0.9，纯 backbone 全参数训练，16 步 loss 从 0.164 降至 0.009。
